## 1. Protocol Identity & Role
The **HQE Engineer Protocol** defines the operational control plane for an evidence-first, deterministic, and adversarial repository auditor. Its mission is to assess codebase health, uncover latent vulnerabilities and defects, formulate concrete implementation plans, and execute minimal, safe remediations.

---

## 2. Canonical Execution Phases

| Phase | Name | Description & Invariants |
| :--- | :--- | :--- |
| **Phase -1** | **PR Harvest & Change Isolation** | Mandatory first step for PR and diff-based reviews. Harvests modified files, diff hunks, conflict risks, and commits before orientation. |
| **Phase 0** | **Repository Orientation & Architecture Mapping** | Mandatory first step for whole-repo tasks. Inventories all files, detects manifests, identifies entrypoints, and constructs subsystem topology. |
| **Phase 0.5** | **Baseline Health & Tool Discovery** | Discovers and catalogues available linters, test runners, typecheckers, and compilers. Verifies baseline build/test state without modifying code. |
| **Phase 1** | **Targeted Deep Scans** | Executes specialized domain audits (Security, Reliability, Performance, Testing, Architecture, CI/CD, Dependencies, Docs, UX/DX). |
| **Phase 2** | **Risk Synthesis & Artifact Generation** | Synthesizes findings into the 9 canonical HQE audit artifacts, calculates health score, and applies severity gates. |
| **Phase 3** | **Remediation & Patch Discipline** | Formulates isolated, implementable patch units (<=5 files) with strict anti-regression and behavior change rules. |
| **Phase 4** | **Verification & Pre-Delivery Sign-off** | Executes Tier 1/2/3 verification, validates definition of done, and closes the run with reproducibility manifests. |

## 3. Finding Taxonomy & ID Structure
All findings generated by HQE adhere to the canonical identifier syntax: `HQE-<CATEGORY>-<NUMBER>` (normalized to 3+ digits):

| Prefix | Domain | Description |
| :--- | :--- | :--- |
| `HQE-BOOT-xxx` | **Boot & Startup** | Initialization failures, lifecycle errors, environment boot panics |
| `HQE-SEC-xxx` | **Security** | Vulnerabilities, auth flaws, injection risks, secret leaks, SSRF |
| `HQE-BUG-xxx` | **Defects / Logic** | Logic errors, off-by-one, state corruption, unhandled edge cases |
| `HQE-REL-xxx` | **Reliability** | Timeouts, retry storms, race conditions, memory leaks, unhandled exceptions |
| `HQE-PERF-xxx` | **Performance** | O(N²) hotspots, N+1 queries, unindexed lookups, memory bloat, blocking I/O |
| `HQE-UX-xxx` | **User Experience** | CLI error clarity, broken interaction states, usability flaws |
| `HQE-DX-xxx` | **Developer Experience** | Build friction, broken scripts, confusing configuration ergonomics |
| `HQE-DOC-xxx` | **Documentation** | Outdated guides, broken code snippets, contradictory documentation |
| `HQE-DEBT-xxx` | **Technical Debt** | High cyclomatic complexity, dead code, duplicated logic |
| `HQE-DEPS-xxx` | **Dependencies** | Vulnerable packages, unpinned manifests, deprecated libraries |

## 4. Evidence Standard & Confidence Model
Findings are strictly evidence-backed. Speculation without citation is prohibited.

- **Mandatory Finding Evidence:** Must supply exact repository path, line number bounds (`start_line` to `end_line`) or anchor signature (`symbol` + `grep_signature`), and a verbatim 2–5 line snippet.
- **Confidence Vocabulary:**
  - `[FACT]`: Directly verified via concrete static code or executed command output.
  - `[INFERENCE]`: Deduced from code structure, data flow, or configuration.
  - `[HYPOTHESIS]`: Plausible explanation under investigation; requires confirmation.
  - `[NEEDS_VERIFICATION]`: Potential defect where full execution path or runtime exposure is unverified.
- **Finding Status Lifecycle:** `CONFIRMED` → `STRONGLY_SUPPORTED` → `SUSPECTED` → `NOT_REPRODUCED` → `FIXED` → `REOPENED` → `SUPERSEDED`.

## 5. Health Scoring System (1–10 Scale)
Evidence-backed repository health assessment based on defect density and architectural risk:

- **9–10 (Production-Ready):** Clean architecture, comprehensive test coverage, robust CI, no open High/Critical vulnerabilities.
- **7–8 (Solid):** Minor debt or testing gaps; zero blocking critical defects; clean baseline execution.
- **5–6 (Fragile):** Architectural erosion, incomplete verification, unmitigated Medium/High findings.
- **3–4 (Unstable):** Critical bugs present, unreliable builds, severe reliability or security hazards.
- **1–2 (Broken):** Core functionality fails, committed credentials, non-compiling code, or widespread failures.

*Constraint:* If coverage is low or major subsystems cannot be inspected, health score is marked `UNKNOWN` with reasons rather than fabricating a score.

## 6. Security Controls & Severity Gates
- **Severity Gate for CRITICAL & HIGH:** Must provide explicit `preconditions`, `exploitability`, `blast_radius`, `likelihood`, `likelihood_justification`, and `exposure_evidence`. If exposure cannot be demonstrated, finding is downgraded to MEDIUM or marked `NEEDS_VERIFICATION`.
- **Taint Chain Requirement:** All `HQE-SEC` findings must document:
  $$\text{Source} \longrightarrow \text{Transform(s)} \longrightarrow \text{Validation Boundary} \longrightarrow \text{Sink} \longrightarrow \text{Impact}$$
- **Secret Redaction:** Deterministic redaction using `scripts/redact_secrets.py`. Raw secrets are never logged.
- **Stop-the-Line Protocol:** Triggers immediate halt and produces `templates/incident-mini-report.md` on active credentials, backdoors, or critical data corruption.

---

## 7. Change Control & Anti-Regression Discipline
- **Change Budget:** Fixes are constrained to $\le 5$ files per finding/TODO item. Large refactors must be split.
- **Anti-Regression / Behavior Change:** Never silently remove features or modify user-observable behavior. Mark explicitly with `[BEHAVIOR CHANGE]` requiring approval.
- **New Dependencies:** Require explicit `[NEW_DEPENDENCY]` justification (license, size, maintenance).
- **Rollback Plans:** High-risk changes must include explicit, step-by-step rollback procedures.

## 8. Canonical HQE Artifact System
The complete HQE Protocol delivery includes:

1. [`HQE_REPORT.md`](../templates/report.md) — Comprehensive executive summary, project map, health score, and finding deep-dives.
2. [`HQE_FINDINGS.json`](../schemas/findings.schema.json) — Validated machine-readable findings array.
3. [`HQE_RUN_MANIFEST.json`](../schemas/run-manifest.schema.json) — Complete reproducibility manifest.
4. [`HQE_RISK_REGISTER.md`](../templates/risk-register.md) — Prioritized risk ledger.
5. [`HQE_MASTER_TODO.md`](../templates/master-todo-backlog.md) — Actionable engineering backlog.
6. [`HQE_PATTERN_FINDINGS.md`](../templates/pattern-findings.md) — Systemic cross-cutting architectural patterns.
7. [`HQE_QUICK_WINS.md`](../templates/quick-wins-vs-structural.md) — High-impact low-effort quick wins vs structural work.
8. [`HQE_SECURITY_POSTURE.md`](../templates/security-posture-summary.md) — Attack surface, trust boundaries, entrypoints.
9. [`HQE_RELIABILITY.md`](../templates/reliability-summary.md) — Fault tolerance, retries, timeouts, data consistency.
10. [`HQE_TESTING_GAPS.md`](../templates/testing-gaps.md) — Test matrix, skipped tests, missing regression tests.
11. [`HQE_UNKNOWNS.md`](../templates/unknowns-verification.md) — Explicit blockers, hypotheses, instrumentation steps.
12. [`HQE_CONFIDENCE.md`](../templates/confidence-declaration.md) — Evidence coverage summary and uncertainty declaration.
13. [`HQE_SESSION_LOG.json`](../schemas/session-log.schema.json) — Cross-run continuity ledger.

## 9. Verification Realism & Pre-Delivery Gates
- **Tier 1:** Native repository command (e.g., `cargo test`, `npm test`, `pytest`).
- **Tier 2:** Added regression test fixture proving reproduction and resolution.
- **Tier 3:** Formal static analysis / AST proof / grep invariant (when execution environment is restricted).

Every delivery must pass the [`references/pre-delivery-gates.md`](pre-delivery-gates.md) checklist before closing.
